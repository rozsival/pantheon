# 🧰 CLI Reference

> `./bin/pantheon` is the single entrypoint for the server baseline: the setup steps, updates of the install itself and
> shell integration. It is generated by [Bashly](https://bashly.dev/) from authored sources in `cli/`; this page is both
> the user reference and the maintainer contract for changing it.

**Related:** [Installation](installation.md) · [Security](security.md) · [Development](development.md)

---

## 📍 At a glance

| Audience           | Use this                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------- |
| CLI users          | `./bin/pantheon` from the install directory, or `pantheon` anywhere after [`install`](#install) |
| CLI maintainers    | Edit authored sources in `./cli/*`                                                              |
| Generated artifact | `./bin/pantheon` is build output, not the source of truth                                       |

> [!IMPORTANT]
> Do **not** edit `./bin/pantheon` directly. Update the authored Bashly sources and regenerate it instead.

## 🗂️ Command groups

| Command       | Purpose                                             |
| ------------- | --------------------------------------------------- |
| `setup`       | Prepare and secure the server                       |
| `update`      | Install another Pantheon version from GitHub        |


## 📖 Command reference

### `setup`

Run with `sudo`. `setup` alone runs `setup all`. Every step asks for confirmation first. Details:
[Installation](installation.md#-run-the-setup).

| Subcommand  | Purpose                                                                | Flags (env var)                                                                                                                               |
| ----------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `all`       | Interactive setup: the core steps, then the extras when accepted       | `-n` `--server-name`, `-u` `--allowed-user`, `-p` `--ssh-port`, `-t` `--timezone`, `-d` `--lvm-device`, `-x` `--extras` (`pantheon_extras=1`) |
| `init`      | Extend the LVM root volume (skipped without one), set the timezone     | `-t` `--timezone` (`pantheon_timezone`), `-d` `--lvm-device` (`pantheon_lvm_device`)                                                          |
| `packages`  | Upgrade the system, install essential packages and unattended upgrades | —                                                                                                                                             |
| `docker`    | Install Docker Engine and Compose, add the user to the `docker` group  | `-u` `--allowed-user` (`pantheon_allowed_user`)                                                                                               |
| `tailscale` | Install Tailscale                                                      | —                                                                                                                                             |
| `ssh`       | Harden SSH                                                             | `-u` `--allowed-user`, `-p` `--ssh-port` (`pantheon_ssh_port`)                                                                                |
| `ufw`       | Deny incoming, allow the SSH port; keep existing rules                 | `-p` `--ssh-port`, `--reset` (delete every rule first)                                                                                        |
| `fail2ban`  | Install and configure fail2ban                                         | `-p` `--ssh-port`                                                                                                                             |
| `brew`      | Extra: Homebrew and `bottom` for the user                              | `-u` `--allowed-user`                                                                                                                         |
| `shell`     | Extra: Starship, Ghostty terminfo, linger for the user                 | `-u` `--allowed-user`                                                                                                                         |

Defaults: SSH port `2222`, the host's current timezone, LVM device `/dev/ubuntu-vg/ubuntu-lv`, the user running `sudo`
and the host name. A flag wins over its env var, which wins over the default.

### `update`

```bash
pantheon update             # the latest release
pantheon update v1.2.0      # a release (the v is optional)
pantheon update feat/x      # a branch: unstable, asks a second time
```

Run as the user who owns the install, never with `sudo`. It resolves the version on GitHub, asks for confirmation,
downloads it and replaces the installed files by rename. Files the new version no longer ships are deleted (they are
listed in `.manifest`), and nothing else in the directory is touched. Downgrades ask a second time. `update` changes
**nothing on the host**: re-run the setup steps whose behavior changed. It needs `jq`, which `setup packages` installs.

### `install`

```bash
./bin/pantheon install    # as yourself, never with sudo
```

Makes `pantheon` a command: a symlink `~/.local/bin/pantheon` onto this install's `bin/pantheon`, and the bash
completion script at `~/.local/share/bash-completion/completions/pantheon` (`$XDG_DATA_HOME` respected), where
bash-completion's lazy loader finds it on the first `<TAB>`. Idempotent; it refuses a `~/.local/bin/pantheon` that is a
real file. `setup all` runs it for the allowed user.

It finishes with checks and exits non-zero if one fails:

| Check           | Passes when                                                                                 |
| --------------- | ------------------------------------------------------------------------------------------- |
| Symlink         | `~/.local/bin/pantheon` points at this install's `bin/pantheon`                             |
| Completion file | It matches what this `bin/pantheon` writes                                                  |
| PATH            | A fresh login shell resolves `pantheon` to the symlink; otherwise it prints the line to add |
| bash-completion | That shell loads bash-completion (Ubuntu's default `~/.bashrc` does)                        |

> [!NOTE]
> `sudo pantheon …` does not find the command: `sudo` uses its own `secure_path`, without `~/.local/bin`. Run setup
> steps as `sudo ~/pantheon/bin/pantheon setup <step>`, or `sudo "$(command -v pantheon)" setup <step>`.

### `completions`

`completions [bash|zsh]` prints the script (default `bash`). For zsh, put `source <(pantheon completions zsh)` in
`~/.zshrc` after `compinit`. Completions are generated natively by Bashly (`completions: full` in
`./bashly-settings.yml`): every `<TAB>` asks the CLI's hidden `__complete` command, so new commands complete as soon
as `bin/pantheon` is rebuilt.

## ✍️ Maintainer workflow

After changing the authored CLI sources, regenerate the CLI (the pre-commit hook also does this):

```bash
pnpm run build:cli
```

### Edit the right files

| Path                      | Responsibility                                                    |
| ------------------------- | ----------------------------------------------------------------- |
| `./cli/bashly.yml`        | Command tree, flags, args, examples, env vars, `version`          |
| `./cli/commands/**/*.sh`  | Command entrypoints (`setup ufw` → `./cli/commands/setup/ufw.sh`) |
| `./cli/lib/*.sh`          | Shared helper logic                                               |
| `./cli/lib/validations/*` | Custom validations                                                |
| `./cli/initialize.sh`     | Globals set before any command runs                               |
| `./bashly-settings.yml`   | Bashly settings (`completions: full`)                             |

### Editing rules

- `./cli/bashly.yml` is the CLI schema source of truth.
- Prefer `bashly generate` **without** `--force`; `--force` can recreate placeholder command files and overwrite
  authored command bodies.
- Update this page's [command reference](#-command-reference) and, for new top-level groups, the
  [command groups](#-command-groups) table.
- Keep the baseline generic: nothing specific to one workload (GPU drivers, an application's packages) belongs here.
- Every default must be overridable by a flag and an env var, and a re-run must not change what the operator did not
  ask for.

### Implementation notes

- Routine status output uses `pantheon_log_info`, `pantheon_log_success`, `pantheon_log_warn` and `pantheon_log_error`.
- Resolve settings with `pantheon_resolve_option '--flag' ENV_VAR 'default'`: the flag wins, then the env var, then
  the default. Bashly exposes an env var declared as `pantheon_ssh_port` as `PANTHEON_SSH_PORT`.
- Follow-ups the operator must do (reboot, re-login, a second SSH session) go through `pantheon_register_action`, so
  `setup all` lists them at the end.
- Quote `args` keys that contain a hyphen after the first character: `${args['--lvm-device']}`, not
  `${args[--lvm-device]}`. The shell formatter parses an unquoted subscript as arithmetic.
- `apt-get` only, never `apt`; use `apt-get upgrade --with-new-pkgs` where `apt upgrade` was meant.

### Validate after changes

```bash
pnpm run check
bash -n ./bin/pantheon
./bin/pantheon --help
```

The `cli-command` agent skill (`.agents/skills/cli-command/SKILL.md`) encodes this workflow step by step.

## ❓ FAQ

### Why must I never edit `bin/pantheon`?

It is regenerated from `cli/` on every `pnpm run build:cli` (and by the pre-commit hook), so hand edits are lost.

### My new command file came out as a placeholder. What happened?

`bashly generate --force` recreates command files from templates. Restore the body from Git and regenerate without
`--force`.
